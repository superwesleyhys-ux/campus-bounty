# Local sample-account entry

The disposable Postgres interaction preview at http://127.0.0.1:3020 now offers **Enter as sample student** and **Enter as sample publisher** on its logged-out screen. These select existing synthetic Alex and Professor identities; they never convert an entered email, create a university identity, verify enrollment, send external email, or enable payment. The current page and detail destination survive sign-in and logout. The header keeps the sample boundary visible after entry.

This path is unavailable in production and ordinary development. `backend/modules/preview-entry.mjs` requires every existing disposable-fixture setting together: development, Postgres, `CAMPUS_DEMO=0`, `.next-interaction`, exact `http://127.0.0.1:3020`, synthetic sender/local port-1 SMTP configuration, and all three loopback database URLs pointing to the same `campus_test_[a-f0-9]{32}` database. It rereads the private fixture metadata each request and requires its database and two distinct UUIDs to match. The database must contain both fixed `alex@campus.example.test` and `professor@campus.example.test` identities with active accounts, verified identities, current affiliations, and enabled institutions/domains. Failure disables entry; there is no general user/email/token selector.

The new endpoint uses existing same-origin and host checks, strict two-role request validation, no-store responses, bounded session creation, and the usual HttpOnly, SameSite=Strict cookie. A new session revokes the supplied prior session in the same transaction; ordinary logout revokes it. It returns no OTP or session token in the body. Row locks use only the existing auth role's user/identity/affiliation permissions; directory rows retain their read-only privileges. The original `readConfig` demo prohibition is unchanged.

Real-email attempts in this exact active fixture return an explicit unavailable-delivery explanation. Outside this fixture, the original approved-domain/OTP authentication runs unchanged. Synthetic OTP requests remain supported for existing local test tooling. The sample UI never asks the user to inspect private code files.

Focused verification: `node --test tests/backend/preview-entry.test.mjs tests/backend/config.test.mjs tests/backend/config-security.test.mjs tests/backend/http-boundary.test.mjs`, `npm run typecheck`, and `node tests/first-entry-browser.cjs`. The browser test starts new contexts without cookies and records desktop/mobile entry, real Marketplace rendering, navigation, logout, detail reentry with the other role, session rotation, input rejection, and persistent sample labels. These prove this local fixture only, not real email delivery or production readiness.
